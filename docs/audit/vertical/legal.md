## Research summary

**Sources** (WebSearch, live — see inline citations) plus **domain
knowledge** (labeled) where the network egress proxy blocked a site
(`docs.retellai.com` is blocked from this environment — WebFetch returned
`EGRESS_BLOCKED`; relied on `packages/adapters/retell`'s own VERIFY-annotated
comments, which are already cross-checked against the `retell-typescript-sdk`
types in `node_modules`, for Retell wire-shape facts).

- Real front-desk/intake protocol, conflict-check discipline, ABA guidance:
  [Talkroute intake checklist](https://talkroute.com/the-ultimate-law-firm-intake-checklist-from-first-call-to-signed-client/),
  [Clio: conflict check process](https://www.clio.com/blog/conflict-check-how-to/),
  [CasePulse conflict checks guide](https://casepulse.com/conflict-checks-for-law-firms/),
  [Smith.ai legal intake cheat sheet](https://smith.ai/blog/legal-intake-cheat-sheet-10-questions-to-ask-leads).
  Consensus: greet → calm → understand → qualify → next steps → close;
  standard fields = contact info, matter type/practice area, case narrative,
  conflict-check data (potential client identity + area of law + nature of
  dispute + opposing-party/related-entity names, checked for
  spelling/nickname/maiden-name variants) **before** any advice or
  engagement, jurisdiction, deadlines (statute of limitations, custody,
  court dates), lead source, budget/fee expectations, communication
  preference. Conflict check must be run by one role and cleared by a
  *different*, senior/attorney role — never self-cleared by whoever took the
  call.
- Legal CRM/PIMS field shape (Clio Grow, Lawmatics — the two market leaders):
  [Clio Grow](https://www.clio.com/grow/),
  [Lawmatics vs Clio Grow](https://hugheyllc.com/blog/lawmatics-vs-clio-grow/).
  Both model intake as: contact/lead record → **matter** (type, opposing
  party, court, statute of limitations, urgency/priority) → conflict-check
  pass/fail → lead-source attribution feeding matter/pipeline reporting, with
  a "matter" as the durable object everything else hangs off of. This
  codebase's chosen anchor integration for legal is **Clio**
  (`docs/MASTER_PLAN.md` line 68 — Wave 2 "alt", pending 10 discovery calls,
  not yet built: `packages/adapters/` has no `legal`/`clio` directory today —
  expected at this stage, not a gap).
- Retell platform facts:
  [Post-call analysis overview](https://docs.retellai.com/features/post-call-analysis-overview)
  (via search snippet, page itself egress-blocked) — post-call custom
  extraction fields (name/description/type: Bool/Text/Number/Enum) are
  configured on the **agent's own Post-Call Data Extraction config**, a
  separate object from the LLM/conversation-flow prompt body; built-ins are
  `call_summary`, `user_sentiment`, `call_successful`.
  [Multi-prompt agent guide](https://docs.retellai.com/build/single-multi-prompt/write-multi-prompt)
  and
  [Function Node overview](https://docs.retellai.com/build/conversation-flow/function-node)
  (via search snippets) — multi-prompt states carry per-state prompt +
  explicit edges + per-state `tools`, transitions read as prompt-graded
  conditions, matching this repo's `RetellMultiPromptState` shape
  (`packages/adapters/retell/src/compiler/types.ts:150-155`, itself already
  confirmed field-for-field against `retell-typescript-sdk` per that file's
  own VERIFY-8 comment — domain knowledge/repo-verification, not re-fetched
  live since the doc site was blocked).
- Domain knowledge (labeled): TCPA/attorney-advertising and unauthorized-
  practice-of-law (UPL) norms — an AI intake agent must never appear to
  give legal advice, predict outcomes, or quote fees beyond a disclosed
  consult fee; "recording disclosure" interacts with two-party-consent
  states the same way as every other vertical.

## Conversation design findings

1. **[BLOCKER]** `packages/templates/src/verticals/legal.ts:80-90` (`conflict_check`) and `legal.ts:91-99`/`100-108`/`110-114` (`open_discovery`/`urgency`/`referral_source`) all declare `allowed_tools: []`. Only the terminal `intake_complete` state (legal.ts:116-123) carries `take_message`, and `transferToHumanState()` (shared/utility-states.ts:16-26, spliced in at legal.ts:124) carries only `transfer_call` — **no take_message fallback**. Consequence: if the caller triggers `human_request` (a global intent reachable from *every* state, by design — legal.ts:149) at any point before `intake_complete` — e.g., right after stating the opposing party's name — the call transitions straight to `transfer_to_human`, which has no tool to persist anything. Everything gathered so far (name, phone, matter type, and critically the **conflict-check answer**) is lost unless the human answering the transfer happens to write it down. This directly contradicts the vertical's own emphasis that the conflict check must be "recorded" and "flagged for human review" (legal.ts:86-88) — there is no structural guarantee it's ever recorded if the call doesn't reach the final state.
   - **Fix:** give `transfer_to_human` (or a legal-specific variant) `take_message` in addition to `transfer_call`, and/or add a global `record_progress`-style mechanism, so a warm transfer or a give-up still writes what's been collected. (utility-states.ts:16-26 is shared by 6 templates, so this is a cross-vertical fix, not legal-only — but legal's data is the highest-stakes case of it, per `docs/VERTICAL_RESEARCH.md`'s "$3.2–6.5k per missed intake call" framing.)

2. **[HIGH]** No `take_message_fallback` state is spliced into `legal.ts` (contrast `auto-repair.ts:150`, `dental.ts:119`, `motel.ts:122`, `restaurant.ts:158`, `veterinary.ts:148`, all of which include `takeMessageFallbackState()`). The give-up ladder text (`GIVE_UP_LADDER_FRAGMENT`, `shared/fragments.ts:29-33`) is present in every legal system prompt via `QUALITY_AND_COLLECTION_FRAGMENT`, telling the model to "stop retrying... move to a transfer or a take-message fallback instead of guessing" — but there is no state/edge for "take-message fallback" to land on. Every other structural escape in this codebase's own design philosophy (see `red-team/structural.test.ts:37-55`, "reachable from any point in the call — structurally guaranteed, not model-discretionary") is a real `global_intent`; the give-up ladder is the one escalation path in `legal.ts` left entirely to model discretion, with no state to fall into if it fires and the caller doesn't want a transfer.
   - **Fix:** splice `takeMessageFallbackState()` into `rawStates` and wire a transition/global-intent path into it (mirroring the other 5 verticals).

3. **[HIGH]** `matter_type` (legal.ts:71-78) has no `extraction` field and no tool. MASTER_SPEC §3.5 explicitly says legal's `practice_areas[]` "feeds matter-type enum" — implying the compiled template should extract a typed enum constrained to the tenant's configured practice areas. As authored, matter type is spoken but never captured as data anywhere except by hoping the model repeats it inside the free-text `take_message.message_text` at the very end. This is the field a real intake system (Clio Grow/Lawmatics — see research above) treats as the primary pivot for every matter record, and it has zero structured existence here.

4. **[MEDIUM]** `open_discovery` (legal.ts:91-99) is (correctly, per SYSTEM_DESIGN §4.1's own framing — "open empathetic discovery a rigid graph would flatten") an unconstrained free-form state — appropriate design, not a defect by itself. But combined with finding #3/#1, it means the single most information-dense part of the call (the actual facts of the case) has **no persistence path at all** except the model's own end-of-call summarization skill. A dropped call anywhere in `open_discovery`→`referral_source` loses the entire narrative.

5. **[MEDIUM]** Identity/returning-caller handling: `lookupCustomerTool()` is declared in `tools: [...]` (legal.ts:152) but never appears in any state's `allowed_tools` — it is dead code in this template. Real legal front-desks (and the vet/dental templates in this same repo) branch on new-vs-existing caller; legal's greeting doesn't attempt it even though the tool exists and is authorized (`caller_number` scope, safe to call). Not necessarily wrong for a first-contact-heavy intake line, but declaring an unused tool is worth either wiring in (e.g., "have you called us before about this matter?" → `lookup_customer` → skip conflict-check-adjacent chit-chat) or removing to keep the compiled agent's tool surface lean (every declared tool round-trips through every state's Retell payload construction in `multi-prompt.ts:32-45`, `toolsByName`, even though unused ones simply never get attached — small but real dead weight).

6. **[LOW]** Non-English / voicemail / silence handling: covered only via the shared generic fragments (`SILENCE_HANDLING_FRAGMENT`, `ESCALATION_TRIGGERS_FRAGMENT` — "you cannot continue confidently in the language the caller is using" → escalate). No legal-specific override, which is fine — but worth noting the same escalation destination gap as finding #1/#2 applies here too (language-mismatch escalation has nowhere structurally reliable to land).

7. **[LOW / testing gap, not a template bug per se]** `red-team/injection-fixtures.ts:84-93`'s legal fixture asserts (as its "expectation," i.e. what SHOULD be true) that "`legal_advice_given` is a declared extraction field on every legal state so a post-call check catches any slip." That half is true at the canonical-template level (verified structurally by `structural.test.ts:79-90`) but the fixture's implied end-to-end guarantee is false given Backend finding #1 below — the red-team suite only proves the *canonical* `AgentTemplate` object carries the field, never that the compiled Retell payload or the live agent config actually extracts it. There is no test anywhere (unit, snapshot, or otherwise) that would have caught the `post_call_analysis_data` gap, because the compiler test suite (`multi-prompt.test.ts`) only golden-file-matches the LLM states payload, never an agent-level "Post-Call Data Extraction" payload — because the compiler never produces one.

## Backend/tool findings

1. **[BLOCKER] `AgentState.extraction[]` is captured by every template author (legal most heavily — every single state) but is completely dropped by the compiler.** `packages/canonical-types/src/agent-template.ts:61` defines `zAgentState.extraction`; `packages/templates/src/verticals/legal.ts:50-56` (`withLegalGuardrail`) appends `{field: "legal_advice_given", type: "boolean"}` to literally every state. But grep across `packages/adapters/retell/src/compiler/*.ts` for `extraction`/`post_call_analysis`/`custom_analysis` returns **zero matches**. `multi-prompt.ts:28-99`, `conversation-flow.ts`, and `single-prompt.ts` build only the conversation body; `agents.ts:56-95`'s `agentBody` (the actual `POST /create-agent` / `PATCH /update-agent` payload) has no `post_call_analysis_data` key at all. Per Retell's own docs (confirmed via search — post-call custom fields are a distinct agent-level config, not part of the LLM/flow body), this means:
   - `call.call_analysis.custom_analysis_data` will never contain `legal_advice_given` (or `classification`/`outcome`/`follow_up_needed`, which every other vertical's post-call enrichment in `voice-events/handler.ts:157-179` also assumes exist).
   - `docs/VERIFY.md:392` already flags this exact mapping as "Low" confidence and asks to "confirm against T2's actual Retell compiler output" — this audit *is* that confirmation: the compiler builds no such output at all. This should be escalated from "unverified assumption" to a known, provable gap.
   - **Fix:** add a step (either in `compileRetellTemplate`/`compileTemplateArtifact` or as a new `agents.ts` input) that projects every state's `extraction[]` into Retell's Post-Call Data Extraction field list (dedup by field name across states, since `legal_advice_given` — and any per-vertical `classification`-style field — repeats on every state) and includes it in the `create-agent`/`update-agent` body. Until this lands, `legal_advice_given`'s compliance alert (`voice-events/handler.ts:194-207`) is unreachable dead code for every tenant.

2. **[BLOCKER] Vertical-specific `dynamic_variable_overrides` are never forwarded to the live call.** `supabase/functions/voice-inbound/handler.ts:120-145` builds `dynamicVariables` from only: `manager_name`, `manager_phone`, `parking_info`, `accessibility_notes`, `accepted_payment_types`, plus computed fields (`business_name`, `assistant_name`, `greeting_hours_context`, etc.). None of `practice_areas`, `consult_fee_cents` (legal), `cancellation_policy`, `insurances_accepted` (dental), `species_treated`/`emergency_referral` (vet), `tow_partner`/`vehicle_makes_serviced` (auto), `deposit_policy`/`rate_table` (motel), `delivery_radius_m`/`min_order_cents` (restaurant) are read from `overrides` at all. For legal specifically: `legal.ts:33` ("This firm handles `{{practice_areas}}`"), `legal.ts:41` ("configured consult fee (`{{consult_fee_text}}`)"), and `legal.ts:75` ("guiding toward one of `{{practice_areas}}`") will all reach Retell as literal, unresolved `{{...}}` text. This is cross-vertical (affects every template with vertical overrides), but for legal it directly defangs the one hard-coded fee guardrail (`NO_ADVICE_GUARDRAIL`, legal.ts:37-42) — the model has no actual number to avoid exceeding.
   - Compounding gap: even if `consult_fee_cents` were forwarded, there is no cents→text formatter anywhere in the codebase (grep for money-formatting turned up nothing) to produce the `consult_fee_text` string the prompt actually references — unlike `cancellation_policy`, which the schema (`zCancellationPolicy`, `agent-template.ts:271-276`) already stores as author-written `.text`, legal's override schema (`zLegalOverrides`, `agent-template.ts:305-308`) only has `consult_fee_cents` (a number), with no parallel `consult_fee_text` field for a tenant/admin to author directly, and no formatter to derive one.
   - **Fix:** extend `voice-inbound/handler.ts`'s `dynamicVariables` construction to forward every field in `dynamicVariableOverridesSchemaForVertical(vertical)`'s shape (or at minimum the ones referenced in `prompt-lint.ts`'s `ALLOWED_DYNAMIC_VARIABLES` allowlist, which already enumerates all of `practice_areas`, `consult_fee_text`, `rate_table`, etc. — that allowlist is effectively the spec for what this handler should be emitting and isn't); add either a `consult_fee_text` field to `zLegalOverrides` (author it directly, same pattern as `cancellation_policy.text`) or a shared cents→spoken-text formatter.

3. **[HIGH]** `take_message` (`supabase/functions/voice-tools/tools/take_message.ts`) is legal's *only* real persistence tool, and its schema (`shared/tools.ts:141-155`: `caller_name?`, `caller_phone`, `message_text`, `callback_window?`) has no structured fields for matter type, opposing party, urgency reason, or referral source — everything must be composed by the model into one `message_text` string (`call_logs.message_text`, a single `text` column — `call_logs.sql:29`). There's also no dedicated legal intake/matter table anywhere in `supabase/migrations` (`grep -rn "conflict\|opposing\|matter_type\|referral_source"` across every migration returns nothing legal-intake-related). This is architecturally consistent with legal being a Wave-2 "alt" vertical with no committed CRM adapter yet (`docs/MASTER_PLAN.md:68`), so the *absence of a Clio push adapter* itself is not a gap at this stage — but the absence of any structured intermediate storage means that even manual/human downstream work (a staff member reading the dashboard before Clio integration exists) has to parse a free-text blob instead of seeing matter type / opposing party / urgency as distinct fields.
   - **Fix (when legal is committed past "alt")**: either a `create_intake`/`create_matter` tool + minimal `legal_matters` table (matter_type enum, opposing_party text, referral_source text, urgency_reason text, conflict_check_status enum, linked to `call_logs`/`customers`), or at minimum structured jsonb on `call_logs.structured_booking_payload` (already exists, vertical-schema'd per SYSTEM_DESIGN §4.4, currently used by booking verticals only) repurposed for legal's intake shape.

4. **[MEDIUM]** `lookup_customer` (`voice-tools/tools/lookup_customer.ts:57-82`) is correctly scoped (`samePhone` check against the live caller ANI, not client-supplied — `lookup_customer.ts:48-55`) but is unreachable in the legal template (finding #5 above) — the authorization discipline here is sound, it's simply never exercised for this vertical.

5. **[LOW]** `takeMessage.ts:42-55`'s SMS notification `insert` only fires `where ac.transfer_number is not null` — if a solo-practitioner tenant hasn't configured a transfer number (plausible for a small legal intake line that only ever takes messages and never transfers), the intake is recorded on `call_logs.message_text` but **no notification ever reaches the firm** — comment at `take_message.ts:38-41` acknowledges this is a known trade-off ("still recorded on call_logs above... regardless of whether this notification send fires") but for legal, where every intake could be a real filed-in-30-days statute-of-limitations matter, silent non-notification is a materially higher-stakes trade-off than for, say, a restaurant reservation follow-up.

## Lean / fast / secure / scalable findings

- **Prompt length / token cost:** `legal.ts`'s `system_prompt` = intro paragraph + `QUALITY_AND_COLLECTION_FRAGMENT` (7 concatenated fragments, `shared/fragments.ts:98-106`) + `NO_ADVICE_GUARDRAIL`. Every one of the 11 compiled states (8 vertical + `transfer_to_human`/`solicitor_deflect`/`safety_emergency`) additionally re-embeds `NO_ADVICE_GUARDRAIL` verbatim into its own `state_prompt` via `withLegalGuardrail` (legal.ts:50-56) — this is intentional redundancy for a hard compliance guardrail (reasonable trade-off, explicitly justified in the file's own header comment) but does mean every state carries the ~50-word guardrail text on top of `general_prompt`, which is sent once — actual per-turn token cost is dominated by `general_prompt` (sent every turn per Retell's LLM mechanics) plus the *current* state's prompt only, so the duplication cost is modest (one extra state_prompt's worth, not all 11). Not a real problem at this state count.
- **State count:** 11 states (`greeting`, `collect_name_phone`, `matter_type`, `conflict_check`, `open_discovery`, `urgency`, `referral_source`, `intake_complete`, `transfer_to_human`, `solicitor_deflect`, `safety_emergency`) plus 3 global intents fanning out edges from (up to) every other state to each of `safety_emergency`/`transfer_to_human`/`solicitor_deflect` (`multi-prompt.ts:68-84`). That's a sane state count for multi_prompt latency — in line with the other 7 templates (`auto-repair`/`dental`/`veterinary` are similarly sized).
- **Tool calls per intake:** at most 1 (`take_message`, once, at `intake_complete`) in the happy path — this is about as lean as a hot-path tool budget gets, well inside the `/voice/tools` p95<500ms budget (BACKEND_SPEC/CLAUDE.md Rule 2). The cost of this leanness is the data-loss/structure gaps documented above — leanness was bought by pushing everything into one end-of-call free-text tool call rather than smaller structured writes along the way.
- **PII/PHI exposure in transcripts/recordings:** legal intake inherently discusses sensitive matter facts (the `open_discovery` narrative could include health info in a PI case, financial info, minors' names in a custody matter) in the recorded/transcribed call — this is arguably unavoidable for a legal intake line (unlike dental's DOB/insurance, which dental correctly defers to a secure post-call form per `structural.test.ts:114-124`), but there is no equivalent "sensitive-topic deferral" instruction anywhere in `legal.ts` even for things that plausibly could be deferred (e.g., don't ask for SSN/account numbers if a caller volunteers them mid-narrative — no guardrail against accidentally capturing that in the recording, unlike the payment-card-number guardrail baked into `sendPaymentLinkTool()`'s description in `shared/tools.ts`). Worth a `docs/BUILD_NOTES.md` entry once legal is prioritized past "alt."
- **Per-vertical config validation:** `zLegalOverrides` (agent-template.ts:305-308) is a thin, valid Zod extension (`practice_areas: string[]?`, `consult_fee_cents: cents?`) and does get validated at the application layer per `dynamicVariableOverridesSchemaForVertical` (agent-template.ts:352-373) — the schema itself is fine; the gap is entirely in the runtime-forwarding pipeline (Backend finding #2), not the schema's shape or its validation.
- **Money in cents:** `consult_fee_cents` correctly typed `zCents` (integer cents) — no violation of CLAUDE.md's money-in-cents rule at the schema layer. The UI gap (Conversation-adjacent finding, `vertical-details/page.tsx:406-435`) is a UX/data-entry-error risk, not a type-safety violation: the input is literally labeled "Consultation fee (cents, optional)" and expects the tenant to type raw cents by hand (e.g. must type "15000" for $150) rather than dollars-with-conversion — a real-world data-entry footgun for a non-technical law-firm office manager, though a UI polish item rather than an architecture defect. **[IN-FLUX — apps/web]**

## Strengths

- The **conflict-check-before-substantive-discussion** ordering is exactly right and matches real ABA/firm practice (research above): `matter_type` → `conflict_check` → `open_discovery`, never the reverse (legal.ts:134-141).
- The prompt is explicit and correct that **the AI must never claim a conflict has "passed" or "cleared"** — that's a human-only determination (legal.ts:87-88) — this is a subtle, correctly-handled UPL/liability trap that a naive implementation would get wrong.
- The **no-advice guardrail is structurally forced onto every single state** (including shared transfer/solicitor/emergency states) via `withLegalGuardrail`, not left to a single top-level system-prompt mention that a long multi-turn conversation could drift away from — good defense-in-depth authoring even though the extraction half of that defense is currently dead (Backend finding #1).
- **Global intents** (`emergency`, `human_request`, `solicitor`) are wired with `reachable_from: "any"`, giving real structural (not model-discretionary) escape hatches for the cases that matter most, matching SYSTEM_DESIGN §4.1's own design philosophy and holding up under the red-team suite's structural assertions.
