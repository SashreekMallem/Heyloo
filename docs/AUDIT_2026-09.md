# Heyloo Full-Repo Audit — September 2026

Consolidated from six parallel audits: backend edge functions, frontend dashboard,
database/RLS, voice+POS integration layer, PRD-vs-brief gap analysis, and a
secrets/git-history sweep. Each finding cites file:line where applicable.

**Bottom line:** the "~75% complete, production-ready" claim in
`IMPLEMENTATION_STATUS.md` is false. Against the new business brief (white-label,
multi-vertical, self-serve, Retell-or-equivalent), real completion is under 20%,
and the deployed system has multiple critical, remotely exploitable security holes.

---

## 1. Critical security flaws (fix/rotate before anything else)

## 2. Correctness & financial bugs

- **POS pushes omit tax and delivery fee** — every taxed/delivery order's POS
  ticket disagrees with what the customer was charged (`pos-push/index.ts:534-754`).
- **Duplicate POS push race** — check-then-act guard on `pos_sync_status`;
  Stripe-webhook retry racing a manual trigger double-prints kitchen tickets
  (`pos-push/index.ts:923-989`).
- **Billing is fabricated:** invoices bill a hardcoded $0.05/min
  (`record_call_usage`) while the real Vapi per-call cost is captured in
  `call_logs.cost` and ignored. Base fee is $99 in code vs $299 in the plan.
  No idempotency — a re-run cron double-invoices. Restaurants that cancel
  mid-month are never billed for that month (`monthly-billing/index.ts`).
- **Cron sync silently skips Clover** — `pos-sync` only handles Square
  (`pos-sync/index.ts:90-121`).
- **Clover/Square webhook handlers map order statuses inconsistently** into the
  same column (`closed→completed` vs `COMPLETED→delivered`); three separate
  places define legal status transitions.
- `createOrder` has no idempotency key — retried tool calls create duplicate orders.
- Dead/broken code path: `vapi-events` `handleFunctionCall` reads
  `toolCall.result?.id` from what is actually a flattened string — never fires.
- Operator-precedence bug in end-of-call status derivation (`vapi-events`).
- Dashboard: most pages render failures as "0 calls / empty table" (no error
  states); orders list hard-capped at 50 with no paging; UTC-only day
  boundaries roll a Pacific restaurant's "today" at 4-5pm local.
- ~250 lines byte-identical between `vapi-events` and `vapi-backfill`; Clover
  token-refresh duplicated **and already drifted** between `pos/index.ts` and
  `pos-push/index.ts`.

## 3. The migrations cannot rebuild the database

- All 8 migrations share version prefix `20250214…` ⇒ alphabetical ordering:
  the RLS-fix and pos-location migrations sort **before** `initial_schema.sql`
  creates the tables they alter. Fresh bootstrap fails.
- Three tables the code depends on are **never created in any migration**:
  `restaurant_pos_locations`, `pos_oauth_sessions`, `refresh_tokens`. ~25
  columns used by code don't exist in migrated schema (`orders.pos_order_id`,
  `orders.pos_sync_status`, `restaurants.manager_phone`, ~20 `call_logs` columns).
  The live schema is unversioned and unreproducible.
- Hard `on delete cascade` from `restaurants` onto orders/invoices/call logs;
  no soft delete — one delete destroys financial/audit history.
- `orders.items` is opaque JSONB with no FK to `menu_items`; Square refunds are
  matched by stuffing a Square payment ID into `stripe_payment_intent_id`.
- No webhook-event dedup table (replay unguarded). Money columns are correctly
  numeric/cents (one thing done right).

## 4. Architecture verdict vs the two-layer plan

- **Voice: ~85-90% of the code is Vapi wire-format-specific.** No abstraction.
  One global `VAPI_ASSISTANT_ID` env var for all tenants; system prompts and
  tool schemas exist **only in the Vapi web dashboard** — not in the repo, not
  in the DB. The only per-tenant knob is `assistant_name`.
- **POS: no adapter interface.** Square/Clover are parallel copy-pasted
  implementations branched on string literals across 6 files (Square menu-pull
  exists 3×). Toast is an enum value with zero implementation (a deleted
  `server/` workspace in git history had one).
- **No booking core.** `order_type` CHECK-constrained to `delivery|pickup`;
  no appointment entity, no availability/calendar, no staff/room resources.
  ~80% of logic is restaurant-specific; maybe 15-20% generalizes (customer
  lookup, phone normalization, SMS, call-log plumbing, RLS patterns).
- **Missing table stakes for an answering service:** no transfer-to-human, no
  voicemail, no after-hours logic, no customer SMS confirmation, and phone
  provisioning is 100% manual (`vapiPhoneProvisioned: false` hardcoded).
- **Verdict: refactor the reusable ~15%, rebuild the rest.** Build Layer 1
  (provider-agnostic voice interface + generic booking core + DB-backed
  per-tenant agent config) as new code; re-platform restaurants onto it as
  adapter #1; mine current code as the reference implementation for business
  rules and Clover/Square API quirks.

## 5. PRD vs the new brief — decisions needed

- PRD.MD:36-38 is literally titled "Why Vapi (Not Retell)" — the docs argue
  against the brief's chosen provider. Reconcile before building.
- Onboarding today is neither self-serve nor agency-manual: a public endpoint
  creating businesses with **no payment step**. No Stripe Checkout initiation
  exists anywhere.
- "Any business type" is cosmetic — no `business_type` field, no booking
  primitives, no dental/motel/real-estate concept anywhere.
- Status docs are unreliable (items marked ✅ and "incomplete" on the same
  line; unstarted beta pre-checked as done). Re-baseline from zero.

## 6. Hygiene

- **~58MB of the 89MB repo is one unreferenced anime-head `.glb`** (committed
  twice: `public/` + `dist/`). Committed stale `dist/` (11 commits behind src).
- Every `.tsx` has a stale compiled `.js` twin; `LandingPage.js` /
  `LandingPage 2.js` are compiled artifacts whose **TS sources were deleted**
  (~1,280 unmaintainable lines). 13 of 19 commits are titled "ain".
- `npm run lint` is broken (eslint 9, no flat config). **No CI at all.**
  Root `package.json` still lists the deleted `server` workspace — breaks
  `npm install`. `.gitignore` covers almost nothing.
- Live Supabase project ref committed in `.cursor/mcp.json`, `supabase/.temp/`,
  docs, and hardcoded as a fallback in `dashboard/src/api/client.ts:6`.
- Good news: no live Stripe/Vapi/Supabase secret keys found in tree, history
  samples, or built bundles — placeholders only. The one real leak is the
  Square token prefix in the historical log file (rotate it).

## 7. Immediate remediation checklist (independent of the pivot)

1. Rotate the Imperial Biryani Cafe Square access token; purge
   `server/server/logs/server.log` from git history (`git filter-repo`).
2. Drop or lock down `get_user_for_login` (revoke from `anon`; never return
   `password_hash`). Rotate the seeded admin password.
3. Make auth mandatory in `restaurants`/`pos` (`verifyAuth(req, true)`) and fix
   `assertRestaurantAccess` to deny when actor is unknown.
4. Remove the fail-open branches in `vapi-tools`, `square-webhook`,
   `vapi-backfill`; add real Clover webhook auth; stop hardcoding
   `payment_status: "paid"`.
5. Hash API tokens; make logout revoke; fix config.toml to match reality.
6. Fix POS push to include tax/delivery fee; add idempotency (orders, invoices,
   webhook event dedup).
7. Repo cleanup: delete `.glb`/`dist`/`.js` twins/dead landing pages, fix
   workspace ref, real `.gitignore`, eslint flat config, minimal CI.
8. Snapshot the live DB schema (`supabase db pull`) into a real baseline
   migration so the database is reproducible.
