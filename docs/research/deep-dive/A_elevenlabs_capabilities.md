### 1.2 Custom tool webhooks — payload, caller-number authority, and auth/signing

| Feature | Status | Citation | Notes |
|---|---|---|---|
| Tool webhook exact request payload shape (path/query/body) | ✓ (configuration-level, not a fixed schema) | [Webhook tools](https://elevenlabs.io/docs/eleven-agents/customization/tools/webhook-tools): you define path params (`{id}` in the URL), query params, and body params (JSON or URL-encoded) **per tool**; the LLM fills their values dynamically from the conversation. | Unlike Retell (which POSTs one fixed envelope `{call, name, args}` to every tool), ElevenLabs tool calls are **shaped entirely by your per-tool config** — there is no single canonical request envelope to build a Zod validator against; the validator has to be per-tool. |
| Request automatically includes the **authoritative caller phone number** | ✗ by default / ✓ if wired | Not documented as an automatic field on tool-webhook requests (confirmed by the tools-overview and webhook-tools pages — no such field is listed). **However**, dynamic variables (including `system__caller_id`, which is populated from the true call session — see §1.1) can be referenced with `{{variable}}` templating in a tool's headers, path, query, or body per the personalization mechanism, and the [dynamic-variable-assignment](https://elevenlabs.io/docs/eleven-agents/customization/tools/webhook-tools#dynamic-variable-assignment) section confirms variables flow tool-configuration-wide. | **Action for our compiler**: every tool definition compiled for ElevenLabs must explicitly inject `{{system__caller_id}}` as a body/header param (not rely on the LLM to "remember" and pass the number itself, which is caller-supplied and unauthoritative — exactly the anti-pattern CLAUDE.md Rule 2 / our `ToolCallRequest.callerNumberE164` field is designed to avoid). This is a **compiler-level requirement**, not a platform guarantee — if we forget to wire it on one tool, that tool silently loses caller authority. Flag as a build-time lint rule for the ElevenLabs adapter. |
| Tool webhook **signature/HMAC verification of the raw body** (Retell-equivalent, CLAUDE.md Rule 2 "verify signature against RAW body first") | ✗ — **not found in current docs** | [Webhook tools §Authentication](https://elevenlabs.io/docs/eleven-agents/customization/tools/webhook-tools) documents only: custom static headers/secrets (`Add Auth` → **Bearer Token**, **Basic Auth**, **OAuth2 Client Credentials**, **OAuth2 JWT**, or a fully custom header name/value) — every one of these is **outbound** auth (how ElevenLabs authenticates *to your third-party API*), configured per-tool. Nothing on this page, the [System tools](https://elevenlabs.io/docs/eleven-agents/customization/tools/system-tools) page, or the [Tools overview](https://elevenlabs.io/docs/eleven-agents/customization/tools) page describes a cryptographic signature ElevenLabs itself attaches to outbound tool-call requests that our receiving server could verify. | **This is the second major decisive gap vs Retell.** Retell HMAC-signs every `/voice/tools` call over the raw body so our fail-closed verifier has cryptographic proof the request came from Retell. ElevenLabs' documented mechanism is instead: configure a static secret (via their secrets manager) as a custom header value on the tool, and our server checks that header equals the expected shared secret. That is **bearer-token auth, not body-integrity HMAC** — it proves possession of the secret, not that the body wasn't tampered with in transit (TLS termination aside) and offers no replay/timestamp protection unless we build our own. If we adopt ElevenLabs, `VoiceProvider.verifyAndParseToolCall`'s "fail closed on missing/invalid signature" contract has to be re-specified as "fail closed on missing/incorrect shared-secret header" — a materially weaker guarantee that should be named explicitly in any ADR, not silently downgraded. **Flagging as VERIFY-worthy**: worth one direct question to ElevenLabs support/sales before relying on it, since "not found in current docs" is not the same as "does not exist." |
| Post-call webhook **does** have real HMAC verification | ✓ | [Post-call webhooks](https://elevenlabs.io/docs/eleven-agents/workflows/post-call-webhooks): header `elevenlabs-signature`; SDKs expose `constructEvent`/`construct_event` (raw body + header + shared secret) which verifies signature, validates timestamp, and parses JSON; endpoint must return HTTP 200 or ElevenLabs retries, auto-disabling the webhook after "10 or more consecutive failures" when the last success was >7 days ago or never happened. | So the call-*ended*/analysis path meets our Rule-2 bar; the call-*tool* (hot) path is the one that doesn't. |
| Tool response can update dynamic variables (state passed forward mid-call) | ✓ | [Webhook tools §Dynamic variable assignment](https://elevenlabs.io/docs/eleven-agents/customization/tools/webhook-tools); [Dynamic variables §Variable Updates from Tools](https://elevenlabs.io/docs/eleven-agents/customization/personalization/dynamic-variables): dot-notation extraction path (e.g. `response.users.0.email`) | Equivalent to our `ToolFallbackResult`/state-mutation pattern conceptually, though mechanically different (assignment-path config, not a typed return envelope). |
| Tool auth methods available | ✓ | OAuth2 Client Credentials, OAuth2 JWT Bearer (HS256 default, configurable claims/kid/expiry), HTTP Basic, static Bearer token via secret, fully custom header | Fine for calling third-party systems (calendars, CRMs); irrelevant to inbound verification (see row above). |
| Timeout / retry behavior on tool webhooks | ✗ — **not found** | Not documented on the webhook-tools page. | Flag for VERIFY — we need this number to size our own hot-path abort budget relative to it, same as we did for Retell's documented 10s retry. |

### Telephony & outbound calling — the most active area this year
- **Exotel added as a first-class telephony provider** alongside Twilio/SIP, with its own outbound-call endpoint and `TelephonyProvider` enum value ([2026-06-01](https://elevenlabs.io/docs/changelog/2026/6/1)).
- **Native Twilio answering-machine detection** (pre-connect AMD, not just LLM-inferred post-greeting detection) shipped this month, with a dedicated webhook event ([2026-09-07](https://elevenlabs.io/docs/changelog/2026/9/7)).
- Direction read: ElevenLabs is broadening carrier support and closing outbound-calling gaps (AMD, batch improvements) rapidly — consistent with a platform investing hard in the telephony/outbound use case specifically, not just chat-to-voice.

### Workflows & agent architecture — converging transfer and workflow primitives
- **Workflow-aware agent transfers**: `transfer_to_agent` can now stay on the *current* agent and jump to a specific workflow node instead of switching agents — merging what used to be two separate concepts (agent transfer vs. workflow navigation) into one ([2026-06-01](https://elevenlabs.io/docs/changelog/2026/6/1)).
- **New workflow `say` node type**: a discriminated literal-text-vs-LLM-generated-prompt message node ([2026-03-02](https://elevenlabs.io/docs/changelog/2026/3/2)).
- Direction read: the node-graph (Workflows) is being actively developed as the primary structured-conversation authoring surface, with steady node-type additions — a positive signal for our "compile target" bet if we ever targeted ElevenLabs' Workflows the way we target Retell's Conversation Flow.

### Data collection & conversation analytics
- **`allowed_values` constraint mechanism** added for data-collection fields (replacing `allowed_values_dynamic_variable`), narrowing the Enum-gap noted in §1.7 somewhat — still not a first-class Enum type, but a documented pattern for constrained values ([2026-09-07](https://elevenlabs.io/docs/changelog/2026/9/7)).
- **`dynamic_variable_params` filters** on conversation listing and transcript text search — lets you query calls by the runtime variable values they carried, e.g. "show me every call where `urgency_flag=high`" ([2026-09-07](https://elevenlabs.io/docs/changelog/2026/9/7)).
- **`workflow_node_entered_id`** conversation filter and **`topic_ids`** search filter, tied to the automatic topic-discovery (Spotlight) feature ([2026-06-01](https://elevenlabs.io/docs/changelog/2026/6/1)).
- **Workspace-wide conversation "triage tickets"** API — a ticketing/inbox layer over conversations, filterable by status/assignee ([2026-09-07](https://elevenlabs.io/docs/changelog/2026/9/7)) — this reads as ElevenLabs building toward a built-in human-handoff/inbox product, which could eventually compete with or complement our own admin cockpit's message-taking flow.
